# Эксплуатация Skladex

Руководство относится к текущему проекту и скриптам `deploy/`. Команды Linux ниже выполняются администратором нового контейнера; секретные значения не передаются в Git, отчётах или аргументах команд. Старый сервер для этих процедур не нужен.

## Состав и размещение

| Компонент | Назначение / расположение |
| --- | --- |
| Nginx | HTTPS, статика, только `public/index.php` передаётся в FPM |
| PHP 8.4 FPM | Пользователь `skladex`, сокет `/run/php/skladex.sock`, отдельный pool |
| Laravel 13 | Код `/srv/skladex/app`; document root `/srv/skladex/app/public` |
| MariaDB 11.8 | БД `skladex`, `utf8mb4`; приложение подключается через локальный сокет |
| Redis | Локальный адрес, пароль; очередь в DB 0, кэш в DB 1, AOF, `noeviction` |
| Файлы | Приватные вложения `storage/app/private`; журналы `storage/logs` |
| Конфигурация | `.env` — ссылка на `/etc/skladex/app.env` |
| Секреты | `/etc/skladex/`; TLS в `tls/`, ключ лицензий `license-master.key` |
| Резервные копии | `/var/lib/skladex/backups` и `/var/lib/skladex/key-backups` |

Node.js и Vite не нужны для production: Blade использует подготовленные файлы `public/assets`, включая локальные шрифты и QR-библиотеку. Внешнего CDN-резерва нет. Время событий — UTC, календарь и отображение — `SKLADEX_TIMEZONE=Asia/Sakhalin`; синхронизация времени ОС важна для сроков и токенов.

## Первичное развёртывание

`provision.sh` предполагает установленную ОС, PHP 8.4 CLI/FPM с расширениями проекта, MariaDB 11.8, Redis, Nginx, Composer, OpenSSL, ACL (`setfacl`), `flock`, `tar`, `gzip` и утилиты MariaDB. Учётные записи `codex-maint`, `www-data`, `redis` и доступ администратора готовятся заранее. Системного пользователя `skladex` скрипт создаёт при отсутствии; пакеты ОС он не устанавливает.

1. Разместить проверенный релиз в `/srv/skladex/app`. От учётной записи развёртывания выполнить `composer install --no-dev --prefer-dist --no-interaction --optimize-autoloader` по `composer.lock`. Не выполнять `composer update` на рабочем сервере.
2. От root выполнить `bash /srv/skladex/app/deploy/provision.sh`. Скрипт создаёт отсутствующие секреты, БД/DB-пользователей, настройки FPM/Nginx/Redis и systemd units очереди, планировщика и резервирования. При отсутствии TLS-ключа создаётся временный самоподписанный сертификат на 30 дней. Production-окружение: `APP_ENV=production`, `APP_DEBUG=false`, шифрованные DB-сессии с secure-cookie, Redis cache/queue, ограниченные host-списки.
3. Применить схему и системный seed, затем собрать конфигурацию от обычного окружения приложения:

   ```bash
   cd /srv/skladex/app
   runuser -u skladex -- php artisan config:clear
   bash deploy/migrate.sh
   chown -R skladex:skladex storage bootstrap/cache
   runuser -u skladex -- php artisan config:cache
   runuser -u skladex -- php artisan view:cache
   runuser -u skladex -- php artisan skladex:check
   ```

   `skladex_app` имеет DML-права без изменения схемы. `migrate.sh` снимает config cache и получает owner-учётку из `/etc/skladex/migrate.env`. Никогда не сохранять owner-учётку в production `config.php`: кэш формируется после завершения скрипта, вне его окружения.
4. Установить доверенный TLS-сертификат и настроить доверие клиентов. Камера требует доверенного HTTPS и разрешения пользователя.
5. Проверить включение `skladex-backup.timer` и выполнить первый архив с проверкой восстановления. Если units обновляются отдельно от полного provision, установить их так:

   ```bash
   install -m 0644 deploy/skladex-backup.service deploy/skladex-backup.timer /etc/systemd/system/
   systemctl daemon-reload
   systemctl enable --now skladex-backup.timer
   ```

6. Передать первому администратору ссылку из защищённого `/etc/skladex/setup-link` по разрешённому каналу, без публикации в журналах/скриншотах. Секрет находится в URL fragment `#token=…`, который браузер не передаёт серверу: локальный JavaScript переносит его в поле формы и очищает fragment. Не заменять fragment на query-параметр. Создание администратора требует этого секрета и пароля от 12 символов. После первого пользователя `/setup` закрывается. Удалить использованную ссылку из оперативного хранения и убрать `SETUP_TOKEN_HASH` из окружения с последующим `config:cache`.

Seed создаёт только 13 категорий: компьютеры, серверы, сеть, периферия, серверные/коммутационные шкафы, комплектующие ИТ, другое ИТ; микрофоны, микшерные пульты, усилители, акустические системы, аудиоинтерфейсы, другое звуковое оборудование. Это справочник, а не утверждение о фактическом наличии техники. Дополнительно создаётся профиль A4 45 × 25 мм, 4 × 10; принтер требуется откалибровать. Пользователей, кабинетов, предметов, лицензий и прежних QR-алиасов seed не содержит.

## Права и чувствительные данные

Вход поддерживает почту либо необязательный уникальный логин (3–64 символа ASCII: a–z, цифры, точка, дефис, подчёркивание). Логин нормализуется в нижний регистр и не содержит @. Изменение логина или почты отзывает сеансы и токены; при собственной смене выполняется выход.

`viewer` читает внутренние данные; `operator` и `admin` ведут учёт, заявки, обходы и обслуживание. Только `admin` управляет пользователями, QR-алиасами и PAT, раскрывает лицензионные ключи. Все роли могут менять свой пароль с проверкой текущего; это отзывает другие сеансы и PAT. Изменение роли/блокировка также отзывает прежние сеансы и токены. Последний активный администратор защищён от отключения; собственную роль и активность изменяет другой администратор.

PAT создаётся администратором для своего пользователя: обязательный `read`, дополнительно `write`, `accept-work`, `reveal-license`, срок 1–365 дней. Полный токен показывается один раз. Для выдачи требуется `SESSION_ENCRYPT=true`; production также использует `SESSION_SECURE_COOKIE=true`. Есть явный отзыв. Права PAT ограничивают роль: администратор с одним `read` не может записывать. Веб-сессия не заменяет Bearer PAT. Критическую работу или работу с отдельным принимающим принимает другой сотрудник.

Публичный whitelist: UUID, код, название, категория, кабинет, учётный статус и состояние. Кабинет публикуется только при `is_public`; скрытие/архивирование закрывает и публичные карточки расположенных в нём предметов. Без входа нет лицензий/ключей, списка ПО, инвентарных/серийных номеров, IP/MAC, ФИО, приватных описаний, документов и истории. Публичный GET не записывает наблюдения инвентаризации. Публичные заявки не предусмотрены.

Вложения выдаются защищённым контроллером с проверкой `read`. Размер одного файла — до 10 МиБ; разрешены PDF, изображения, TXT/CSV, DOCX/XLSX. Не публиковать `storage/app/private` через Nginx или симлинк. Отдельная антивирусная обработка не реализована.

`APP_KEY` защищает данные приложения/сессий. Отдельные `LICENSE_MASTER_KEY_FILE` и `LICENSE_KEY_ID` нужны для лицензионных ключей. Потеря нужного ключа делает дешифровку невозможной. Простая замена файла/ID не является ротацией: текущий шифратор не содержит хранилища нескольких версий. Ротация требует отдельной процедуры с перешифровкой и проверкой восстановления. `bootstrap/cache/config.php` также содержит секреты конфигурации; защищать его как `.env`, не включать в обычный артефакт кода.

## QR и прежние метки

`APP_URL` — адрес приложения, `QR_BASE_URL` — база печатаемых QR. `APP_ALLOWED_HOSTS` ограничивает входящие Host, `QR_ALLOWED_HOSTS` — распознаваемые хосты сканированных ссылок. Эти списки входят в `config/skladex.php`; после изменения окружения пересобрать config cache. Адреса `/p/a/{uuid}` и `/p/r/{uuid}` не зависят от числовых PK. Новые коды генерирует сервер. Инвентарный номер не является уникальным ID.

Сканер передаёт строку локальному resolver: тот разбирает разрешённые формы/хосты, не открывает URL и не обращается к указанному серверу. Чужой URL остаётся неизвестным. Старые `EQ-*`, числовые ID и Unicode-ID кабинетов работают после создания явных алиасов `asset-code:…`, `asset-id:…`, `location-id:…`. Алиас не переназначается на другую цель. Нельзя вычислять EQ из ID. В инвентаризации кабинетная метка не подтверждает все вещи; отправка её как предмета даёт 422. Подробности — в [руководстве переноса](migration.md).

## Регулярные проверки

```bash
systemctl --no-pager --full status nginx php8.4-fpm mariadb redis-server skladex-queue.service
systemctl list-timers --all 'skladex-*'
cd /srv/skladex/app
runuser -u skladex -- php artisan skladex:check
runuser -u skladex -- php artisan schedule:list
journalctl -u skladex-scheduler.service -u skladex-queue.service -u skladex-backup.service --since today --no-pager
```

`/up` проверяет доступность Laravel; `skladex:check` — БД, Redis и пробное шифрование/дешифровку без вывода секрета. Они не проверяют камеру, принтер или полноту бэкапа. Возраст последнего архива, свободное место, ошибки и срок TLS контролируются отдельно; внешнего мониторинга скрипты не устанавливают.

`skladex-scheduler.timer` запускает `schedule:run` каждую минуту. Сроки ТО и внутренние напоминания генерируются раз в пять минут с защитой от пересечений; просроченные ключи повторов и PAT очищаются ежедневно. `php artisan skladex:maintenance` вручную запускает ту же идемпотентную генерацию. Она не выполняет обслуживание и не принимает результат. `MAIL_MAILER=log` означает отсутствие почтовой доставки; Telegram не подключён.

Redis ограничен 128 МиБ с `noeviction`: при заполнении кэш/очередь могут отвечать ошибками. Контролировать память и причину заполнения. Полная очистка Redis удалит очередь и блокировки; `FLUSHALL` не является штатным исправлением.

## Резервирование и восстановление

```bash
bash /srv/skladex/app/deploy/backup.sh
bash /srv/skladex/app/deploy/verify-backup.sh /var/lib/skladex/backups/skladex-TIMESTAMP.tar.gz
```

Backup timer назначен на 03:20 `Asia/Sakhalin` с задержкой до пяти минут. `backup.sh` делает транзакционный дамп MariaDB, добавляет `storage/app/private`, проверяет gzip и пишет SHA-256. В отдельный архив попадает `/etc/skladex` с конфигурацией, паролями, ключами и TLS. Локальная ретенция — 14 дней; каталоги доступны root. Архивы gzip не зашифрованы. Раздельные каталоги на одном диске не защищают от потери контейнера.

Организовать копирование обоих наборов за пределы контейнера после успешного создания и проверки. Доступ к ключам должен быть отдельным и уже доступа к резервным данным; для передачи/хранения нужны защищённый канал и шифрование. Внешнее хранилище, его ретенция и учётные данные пока не настроены. Проверять успешную внешнюю копию до истечения локальных 14 дней. Отдельно сохранять проверенный релиз/`composer.lock` для совместимого восстановления.

Дамп БД согласован транзакционно, но копирование вложений не атомарно относительно БД. Для контрольной копии перед обновлением остановить запись и фоновые процессы, дождаться окончания текущих запросов. Ночной архив не гарантирует единый момент для параллельно загружаемого файла и его строки БД.

`verify-backup.sh` требует соответствующие data- и keys-архивы одного timestamp. Он сверяет SHA-256 обоих архивов, восстанавливает дамп в зарезервированную `skladex_restore_test`, выполняет `mariadb-check` и подсчёты. Для каждой строки `documents` проверяются допустимый путь и SHA-256 фактических байтов из tar. Затем из отдельного keys-архива извлекается master key, и root-команда `skladex:verify-restored-keys` расшифровывает все `license_secrets` восстановленной БД через локальное root-соединение, не выводя значения. Временные БД/файлы удаляются. Не использовать `skladex_restore_test` для иных задач: cleanup удаляет только созданную им временную БД; существующую БД с таким именем скрипт не заменяет.

На начальном пустом production нет реальных документов и лицензий: успешная проверка такого архива подтверждает инфраструктурную процедуру, но ещё не сохранность будущих рабочих вложений/ключей. Загрузка и дешифровка проверяются тестовыми HTTP fixtures; после появления реальных данных повторить backup/verify. Скрипт не запускает восстановленный веб-сервис и не проверяет вход или бизнес-сценарии. Для старого архива требуется совместимый релиз и соответствующий ID ключа; автоматического keyring нет.

Полная репетиция выполняется в изолированном контейнере с соответствующим релизом: проверить хеши; восстановить БД под отдельным именем и приватные файлы; вернуть соответствующие `APP_KEY`, ключ лицензий и ID из архива ключей; настроить отдельный адрес и кэш, не запускать рабочие очереди; пересобрать config cache; проверить вход, документы по SHA-256, дешифровку контрольной лицензии и итоговый отчёт инвентаризации. До принятия результата не переключать рабочий адрес. Для восстановления production сначала сохранить текущее состояние и остановить запись; проверочный скрипт не является автоматическим rollback.

## Сертификат и адрес

Состояние на 16.10.2026: на `192.168.110.203` установлен сертификат от `VVE-Root-CA`, действующий до **15.10.2027 21:54 UTC**. Проверка доверия Windows curl прошла. DNS `skladex.vve.local` уже указывает на `192.168.110.203`; запись изменил пользователь вне этой работы. Скрипты Skladex DNS не изменяют.

Для замены подготовить полную PEM-цепочку, незашифрованный приватный ключ и доверенный CA-файл вне репозитория. От root:

```bash
bash /srv/skladex/app/deploy/install-certificate.sh /secure/fullchain.pem /secure/private.key /secure/trusted-ca.pem
```

Скрипт проверяет срок более суток, цепочку/назначение, имя `skladex.vve.local` и соответствие ключа, сохраняет предыдущую пару, проверяет Nginx и выполняет reload. При ошибке `nginx -t` возвращает прежнюю пару. Проверить с клиентской машины `curl.exe -I https://skladex.vve.local/` без отключения TLS-проверки; проверить issuer/SAN/срок через OpenSSL. Доверие CA на клиентах устанавливается отдельно. Для доступа по IP нужен отдельный IP SAN: скрипт проверяет доменное имя. Автопродления и оповещения об истечении нет; перевыпуск планируется заранее.

При смене домена согласовать DNS, сертификат/SAN, `APP_URL`, `QR_BASE_URL`, разрешённые hosts и прежние печатные ссылки. QR с буквальным старым IP не исправляется изменением DNS: встроенный сканер может разобрать его при разрешённом хосте, но обычная камера откроет старый IP. Перенаправления старого адреса — отдельная согласуемая операция.

## Обновление

Сначала проверить релиз в отдельной тестовой копии и изучить миграции. Не переносить её `.env`, кэш или БД в production. Для текущего расположения, от root:

```bash
cd /srv/skladex/app
runuser -u skladex -- php artisan down --retry=60
systemctl stop skladex-scheduler.timer skladex-scheduler.service skladex-queue.service
# Дождаться завершения текущих web-запросов; исключить параллельную запись.
bash deploy/backup.sh
# Установить проверенный релиз и composer.lock; сохранить /etc/skladex и storage.
# Зависимости установить по lock, без composer update, без Node/Vite.
runuser -u skladex -- php artisan config:clear
bash deploy/migrate.sh
chown -R skladex:skladex storage bootstrap/cache
runuser -u skladex -- php artisan config:cache
runuser -u skladex -- php artisan view:cache
runuser -u skladex -- php artisan skladex:check
nginx -t
php-fpm8.4 -t
systemctl reload php8.4-fpm nginx
systemctl start skladex-queue.service skladex-scheduler.timer
runuser -u skladex -- php artisan up
```

`config:cache` обязателен после изменения окружения/ключевого файла. При изменении unit-файлов сначала установить их и выполнить `systemctl daemon-reload`. Queue workers перезапускаются после замены кода; в примере они остановлены явно. `deploy/activate.sh` восстанавливает права на код/приватные файлы, собирает config/routes/views, проверяет зависимости и конфигурацию, перезапускает worker и перечитывает FPM/Nginx. Скрипт запускается от root после установки зависимостей и миграций, без credentials владельца схемы в окружении; запись на время обновления контролируется отдельно. Проверить HTTPS, вход, чтение и журналы. При ошибке миграции не открывать запись и не запускать произвольный `migrate:rollback`: обратная совместимость схемы и возврат определяются релизом; при необходимости восстанавливается проверенная согласованная копия.

Не запускать `provision.sh` при каждом обновлении: он перезаписывает инфраструктурные настройки и перезапускает БД/Redis/FPM. `CREATE USER IF NOT EXISTS` не меняет существующий MariaDB-пароль; удаление отдельных файлов паролей и повторный provision не является ротацией.

## Тестирование

Feature-тесты используют миграции и отдельную MariaDB 11.8. У тестового пользователя есть права только на отдельную БД `skladex_test`. Нужен отдельный checkout с dev-зависимостями, без production config cache, ссылки на production `.env` и рабочих вложений. Пример из тестовой копии, от операционной учётной записи с доступом к test.env:

```bash
composer install --prefer-dist --no-interaction
set -a
source /etc/skladex/test.env
set +a
export APP_ENV=testing DB_CONNECTION=mariadb DB_HOST=localhost DB_SOCKET=/run/mysqld/mysqld.sock
export DB_URL='' CACHE_STORE=array SESSION_DRIVER=array QUEUE_CONNECTION=sync MAIL_MAILER=array
export APP_KEY="base64:$(openssl rand -base64 32)"
export LICENSE_MASTER_KEY="base64:$(openssl rand -base64 32)"
[[ $DB_DATABASE == *_test ]] || { echo 'Нужна отдельная *_test БД'; exit 1; }
[[ ! -f bootstrap/cache/config.php ]] || { echo 'Недопустим кэш production-конфигурации'; exit 1; }
php vendor/bin/phpunit --colors=never
```

`phpunit.xml` задаёт MariaDB, `skladex_test`, синхронную очередь и временные session/cache. `Tests\TestCase` дополнительно отказывает БД без тестового имени; это защита от ошибки, не замена отдельным DB-правам. Тестовые ключи генерируются отдельно, production-ключи не нужны и не копируются.

`deploy/test.sh` работает относительно своего checkout, запрещает config cache и проверяет суффикс `_test`. Он генерирует отдельные временные ключи приложения/лицензий и запускает PHPUnit от системного пользователя `skladex`; test.env читает учётная запись развёртывания. Для работающего сервиса использовать отдельную копию, например `/srv/skladex/test-release`, и вызывать скрипт из неё. Рабочая конфигурация и вложения туда не копируются. `composer test` запускает PHPUnit и требует того же изолированного окружения; на production тесты не выполняются.

## Особенности текущих deploy-файлов

- Порядок миграции → config cache обязателен: `migrate.sh` снимает кэш, но не пересобирает его. Сборка выполняется отдельно без owner-окружения.
- Worker имеет `--timeout=120`, Redis `REDIS_QUEUE_RETRY_AFTER=180`. При увеличении timeout увеличить retry_after с запасом, пересобрать config cache и перезапустить worker; иначе возможна повторная обработка ещё работающего задания.
- Проверка архива включает БД, байты документов и дешифровку лицензий. Внешнее резервирование, запуск полностью восстановленного экземпляра, мониторинг и продление TLS не автоматизированы. Для тестов требуется отдельный checkout; `test.sh` выбирает каталог собственного расположения.

Это границы текущих скриптов; сама документация не изменяет инфраструктуру.
