# Skladex API v1

Живой справочник: `/api-reference`, JSON OpenAPI 3.1.1: `/api-reference/openapi.json`. Оба адреса доступны только после входа с правом `read`. Базовый путь API — `/api/v1`. В OpenAPI пути уже включают этот префикс; не добавляйте его второй раз. Контракт строится из явных схем приложения и фактического набора маршрутов. Добавление API-маршрута без описания приводит к ошибке покрытия, а не к публикации пустой схемы.

Формат основан на [официальной спецификации OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html). Никакие пакеты генерации, CDN, внешние скрипты и интерактивное исполнение запросов для справочника не используются.

## Авторизация и права

Создайте персональный Bearer PAT через настройки Skladex. Каждый запрос API требует активного пользователя, действительного Laravel Sanctum PAT и способности `read`. Сессия веб-интерфейса не заменяет PAT. Передавайте:

```http
Authorization: Bearer <PAT>
Accept: application/json
Content-Type: application/json
```

Для изменения дополнительно нужен `write`, для принятия и коррекции закрытых работ — `accept-work` (общий контур изменения также требует `write`). Отклонение результата через `reject_result` требует `accept-work` дополнительно к `write`. Открытие лицензионного ключа требует `reveal-license` и роли администратора; `write` для самого открытия не нужен. Добавление первого ключа доступно оператору с `write`; замена уже сохранённого ключа требует администратора и `reveal-license`. Права токена ограничивают возможности роли, не расширяют их.

Viewer читает, operator/admin изменяют и принимают работы. Даже администратор с токеном только `read` не может менять записи. Критическую работу и работу с `requires_other_acceptor` принимает другой уполномоченный сотрудник.

## Идентификаторы и форматы

- В адресах `assets/{asset}`, `locations/{location}`, `buildings/{building}`, `software/{software}`, `licenses/{license}`, `kits/{kit}`, работ, заявок, планов, сроков и кампаний используется UUID.
- `id` и связанные `category_id`, `location_id`, `asset_id`, `software_product_id`, `software_release_id`, `software_installation_id`, `owner_id`, `assignee_id` — числовые ID. Компоненты, установки и лицензионные привязки используют числовой ID и в пути.
- Поля с явным суффиксом `_uuid` и `target_ids` печати — UUID. `inventory_no` не уникален и не заменяет ID, UUID или QR-код.
- Новые коды `SKX-A-*`, `SKX-R-*`, `SKX-L-*` генерируются сервером. Старые QR обслуживаются отдельным типизированным resolver; не стройте код `EQ-*` из числового ID.
- Календарный ввод: `YYYY-MM-DD`. Времена событий в ответах — ISO8601/UTC. Для `completed_at` рекомендуем RFC3339 с явным offset; время без offset считается временем `Asia/Sakhalin`. Фактическое выполнение в будущем запрещено.
- Eloquent может сериализовать календарные даты как ISO8601 с нулевым временем. DECIMAL (стоимость, размеры профилей) может приходить строкой, сохраняющей точность.

Категории получают через `GET /api/v1/categories`: `{data:[{id,name,slug,domain,kind,maintenance_policy}]}`. Пользователей первоначально выбирают через внутренние настройки; отдельного API управления пользователями и изменения категорий в v1 нет.

## Здания и кабинеты

`GET /api/v1/buildings` возвращает активные здания с количеством активных кабинетов (`locations_count`), по 50 зданий на странице. `GET /buildings/{uuid}` возвращает `{data,locations,meta}`: сведения о здании и до 50 его активных кабинетов. Адрес доступен авторизованным пользователям, приватные `notes` в JSON не возвращаются. `POST /buildings` принимает `name`, необязательные `address` и `notes`; `PATCH /buildings/{uuid}` — те же поля и `expected_version`. Эти команды требуют `write` и `Idempotency-Key`.

Кабинет связывается со зданием полем `building_id` (числовой ID) в создании или редактировании кабинета. Явный `null` снимает связь, отсутствие поля при редактировании сохраняет прежнее значение. Можно выбирать только действующее здание. У имущества отдельного редактируемого `building_id` нет: здание определяется через текущий кабинет. Изменение здания кабинета не переписывает размещение его имущества.

Фильтр `building_id` у `GET /locations` и `GET /assets` принимает числовой ID здания или `unassigned`. Перенесённые из старой системы кабинеты первоначально остаются без указанного здания; их распределяет сотрудник. `POST /buildings/{uuid}/archive` принимает `expected_version`; любой активный кабинет, включая пустой, блокирует архивирование. Архивирование сохраняет здание и исторические ссылки. Новые здания создаются через интерфейс или API, их количество не ограничено двумя.

## Повтор команд и версии

Изменяющие POST/PATCH требуют заголовок `Idempotency-Key`: 16–100 символов `[a-zA-Z0-9_.:-]`, например UUID. Уникальность — в пределах пользователя. Повтор неизменного метода, пути и JSON с прежним ключом возвращает исходный успешный ответ. Другой запрос с тем же ключом даёт `409`; изменение типов, состава или порядка вложенного JSON при повторе может считаться другим запросом. Не используйте ключ повторно для другой команды. Неуспешная команда и её изменения откатываются. Веб-формы также используют совместимый внутренний `idempotency_key`; интеграции должны использовать HTTP-заголовок.

Исключения: `POST /licenses/{uuid}/reveal` и чтение `POST /labels/preview`, `/labels/pdf`, `/labels/test`. Они не требуют ключ и не сохраняют ответ в таблице повторов. Остальные API-изменения проходят общий контур идемпотентности.

`expected_version` получают из актуальной карточки перед изменением. После `409` перечитайте ресурс, разберите изменение и отправьте новую осмысленную команду с новым Idempotency-Key. Простое увеличение номера версии без сверки данных недопустимо.

Особые владельцы версии:

| Команда | expected_version |
|---|---|
| Добавить выпуск/установку ПО | Программа |
| Изменить установку ПО | Установка |
| Выдать/освободить место, заменить/открыть ключ | Лицензия |
| Добавить/снять компонент | Родительский ПК |
| Разместить предмет в rack | Дочерний предмет; дополнительно expected_rack_version шкафа |
| Снять предмет с rack | Дочерний предмет |
| Изменить состав комплекта | Комплект |
| Решить retry/skip для срока ТО | Родительский план |
| Наблюдение/решение/переход кампании | Кампания; для решения по предмету также asset_expected_version |

Наблюдения сами по себе не увеличивают версию кампании. Изменение установки ПО увеличивает её версию и версию программы. Приёмка может изменить версию связанного плана.

## Пример: лицензия и ПК

Ниже значения демонстрационные, команды справочник не выполняет. Числовые ID берутся из реальных ответов каталога/имущества.

```http
POST /api/v1/licenses
Idempotency-Key: 4a1bf59b-e54c-4868-91d4-03210741dd51
Content-Type: application/json
Authorization: Bearer <PAT-with-read-write>

{"software_product_id":12,"license_key":"<введите секретный ключ>","asset_id":34,"metric":"device","capacity":1}
```

Ключ и ПК необязательны. Программа обязательна; никаких обязательных договоров. Ответ `201` содержит `{license, warnings, usage}`. UUID и `version` лицензии используйте в последующих командах. `GET /licenses/{uuid}` добавляет историю `assignments`, но никогда не возвращает секрет, ciphertext или key_id. `POST /licenses/{uuid}/key` позволяет добавить ключ позднее, либо явно заменить его с дополнительными правами.

Для `metric=device` известная capacity проверяется под блокировкой; превышение и повторная активная привязка одного ПК отклоняются. Для `user`, `instance`, `unknown` связи с ПК справочные: `usage.remaining=null`, `needs_review=true`, автоматического вывода о соответствии лицензии нет. При неизвестной capacity запись разрешена с предупреждением. Один общий volume key разрешён для нескольких мест/записей; одинаковый ключ не требует глобальной уникальности.

```http
POST /api/v1/licenses/{license-uuid}/reveal
Authorization: Bearer <admin-PAT-with-read-reveal-license>
Content-Type: application/json

{"expected_version":1}
```

Ответ содержит настоящий секрет и `Cache-Control: no-store`. Не логируйте тело, не сохраняйте его в мониторинге/кеше. Открытие записывается в аудит. Мастер-ключ хранится вне БД, имеет отдельный резервный экземпляр; API его никогда не выдаёт.

## Имущество, ПО и обслуживание

Предмет, помещение, rack и логический комплект различаются. `rack_id` — числовой ID самостоятельного актива типа rack; вместе с ним передают `expected_rack_version`. Компонент-описание — строка состава, не самостоятельный актив. Для уже учтённого комплектующего используется `child_asset_id` и `expected_child_version`, без копирования карточки; один физический родитель и отсутствие циклов проверяются сервером. Перемещение выполняется через `/assets/{uuid}/move`, с причиной и обязательно явным `location_id` (числовой ID или null). Для содержимого нужны `include_children=true` и `expected_contents:{"UUID":version,...}` всех физических потомков из текущей карточки. При изменении состава/версий сервер вернёт 409. Оставшиеся предметы сначала отсоединяются. `PATCH /assets/{uuid}` не принимает изменение location_id/status: используйте move. Подробная внутренняя карточка имущества содержит private_notes/specifications и не предназначена для гостевой публикации.

ПО разделено на продукт, выпуск и фактическую установку/сервис. Установка требует оборудование или непустую среду (ВМ/контейнер/внешний сервис). Выпуск должен относиться к продукту. Изменение записанной версии не запускает обновление. `verified_now=true` подтверждает ручную проверку факта сейчас; при смене версии/размещения предыдущая проверка сбрасывается. Секреты инфраструктуры хранятся внешними ссылками; репозиторий не должен содержать пароль/токен в URL.

У работы/заявки/регламента ровно один объект: `asset_uuid` либо `software_installation_id`. Жизненный цикл работы: `open → in_progress/on_hold → completed → closed`, отдельно отмена и возврат результата. Запись через `/maintenance/completed-work` атомарно создаёт выполненную работу, но не подменяет приёмку.

Checklist задаётся массивом `{key,label,type,required}` (до 100 шагов). Ответы: `checklist_answers: {"step_key":{"value":...,"note":...}}`. `check` — bool/0/1, обязательный check требует true/1; `inspection` — pass/flag/fail/na, для flag/fail/na нужно непустое пояснение; `number` — конечное число; `text` — до 10000 символов. Расходники: `materials:[{name,quantity,unit_cost?}]`. Принятие результата не исправляет состояние имущества автоматически. Замечания inspection создают последующую работу.

План ТО может быть календарным или от фактического выполнения. Неизвестная дата не считается фактом ТО. Срок хранит снимок расписания; при приёмке зачёт считается от `completed_at`, а не от даты нажатия «Принять». `generate` может вернуть `work:null`; пропуск completion-плана не создаёт выдуманную дату выполнения. Текст закрытого результата исправляют отдельной correction с причиной, без изменения дат и зачёта.

## Инвентаризация

Создание задаёт фильтры `location_uuids`, `category_ids`, `asset_uuids`; пустая область означает всё, заданные фильтры соединяются AND, помещения включают потомков. `start` формирует снимок состава и блокирует пересечение активных кампаний. Наблюдение хранит точный код предмета, помещение, состояние, автора и версию; не перемещает и не «лечит» имущество. Для повторов сохраняйте тот же `client_key` одного наблюдения.

`reconcile` останавливает приём наблюдений. Решения append-only, последнее действует только для актуальной версии предмета. `move` требует свежее наблюдение данного предмета, `follow_up` — назначенного ответственного, `ignore_unknown` — неизвестную метку. Перед `close` разберите все отклонения, extra и unknown. Итоговый payload замораживается; новые предметы не увеличивают первоначальное expected. Просроченные наблюдения и устаревшие решения требуют повторной проверки. Сканирование кабинета/шкафа не подтверждает всё содержимое.

## Наклейки

`GET /labels` возвращает профили, геометрию и до 500 объектов, `truncated` показывает усечение. Выбирайте `target_type=asset|location`, `target_ids` — UUID. Список не может содержать дубликаты. `start_cell` начинается с 1, ячейки идут по строкам; последующие листы — с первой ячейки. Максимум 500 меток и 50 листов за запрос.

Размеры профиля в миллиметрах с точностью 0.01. Все поля геометрии обязательны для сохранения профиля; для preview/pdf/test достаточно profile_id и/или выборочных переопределений, иначе используются системные параметры. Каждая сторона бумаги — 50–420 мм; доступны A4/A3/A5 и свой размер, книжная и альбомная ориентация. Сетка с полями и offsets должна полностью помещаться на листе, `rows×columns≤500`. PDF формируется локально, без удалённых изображений. Тестовый лист содержит контрольный отрезок 100 мм по каждой оси со стороной не короче 120 мм. Печатайте 100% / Actual size с отключённым Fit to page; параметры принтера не определяются автоматически.

## Ответы и ошибки

Форма ответа описана у каждой операции: нет единого универсального envelope. Имущество/помещения используют `data`, ПО возвращает объект напрямую, лицензии — `license/warnings/usage`, операции обслуживания — модель, отчёт кампании — отдельный payload. Списки имеют фиксированный размер страницы. Laravel paginator содержит `data/current_page/last_page/per_page/total`; некоторые исходные контроллеры используют собственный `meta` или только `data`. Не требуйте отсутствующие поля у всех разделов.

`401` — отсутствует/недействителен PAT; `403` — роль/способности/приёмка; `404` — ресурс отсутствует; `409` — версия, состояние, конфликт повторов/наблюдений; `422` — валидация или доменное правило; `429` — лимит запросов; `500` — ошибка сервера. JSON содержит `message`, при полевой валидации — `errors:{field:[messages]}`. Некоторые доменные 422 возвращают только `message`; не считайте наличие errors безусловным. После временной ошибки сохраняйте ключ команды и сначала проверяйте результат.

Публичные QR-страницы — отдельный ограниченный интерфейс. Этот API не делает внутренние сведения, лицензии, IP, репозитории, документы и приватные заметки публичными.
