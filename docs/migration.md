# Перенос прежнего Skladex

Перенос выполняется явной командой администратора после резервирования и пробного запуска. Обычные миграции схемы, seed и запуск приложения данные прежнего сервиса не загружают. Старый сервер используется только для чтения; его БД, файлы и конфигурация не изменяются.

## Снимок и область переноса

Экспорт `skladex-legacy-v1` — UTF-8 JSON с `source.system=skladex-v1`, `source.timezone=UTC`, датой экспорта и девятью полными таблицами в `tables`: users, cabinets, categories, equipment, equipment_moves, equipment_status_history, attachments, audit_log, qr_codes. Пароли, их хеши и токены в бизнес-экспорт не включаются. Полный SQL-архив хранится отдельно с ограниченным доступом, вне Git и web root.

Перед переносом проверяются восстановление старого SQL-архива и новой резервной копии. Затем на отдельной БД с суффиксом `_test` восстанавливается копия нового сервиса, применяются схема и импорт, проверяются сопоставления и сохранность исходных записей. Тестовый импорт не использует рабочую БД.

Согласованный перенос сохраняет всё имеющееся техническое оборудование: ИТ, звук и сценический свет. Мебель не добавляется. Исходные 13 категорий сохраняют названия; свет получает область `stage`, звук — `audio`, остальные — `it`. Предмет без категории получает отдельную категорию `unknown`. Системный справочник нового сервиса не удаляется.

## Явный запуск

Файлы экспорта должны находиться в защищённом каталоге вне `public`. Команды ниже запускаются на новом сервере из корня приложения с обычной конфигурацией приложения. Сначала применяется схема от миграционной учётной записи, затем config cache собирается с обычными DML-правами согласно `operations.md`.

```bash
# Только проверка: без изменения данных.
php artisan skladex:legacy-import /private/path/legacy-dataset.json

# Применение: ID существующего активного администратора, не старый ID пользователя.
php artisan skladex:legacy-import /private/path/legacy-dataset.json --apply --actor=ADMIN_ID
```

Проверка возвращает SHA-256 нормализованного набора, количества, предупреждения и конфликты. При конфликте применять нельзя. Перед рабочим запуском создаётся свежая резервная копия, временно закрывается запись через maintenance mode и останавливаются фоновые задания; после сверки работа возобновляется.

Изменения выполняются одной транзакцией с блокировками. `legacy_imports` хранит источник, хеш набора, администратора, время и итоги; `legacy_records` — точные исходные строки без учётных секретов, их хеши и соответствия новым ID/UUID. Повтор того же набора ничего не создаёт. Изменение уже перенесённой исходной строки отклоняется: импорт не перезаписывает последующие правки в новом сервисе. Новые строки можно переносить следующим проверенным набором; удаления в старой системе автоматически не удаляют предметы в новой.

Существующие предметы, кабинеты, категории, профиль печати и администратор сохраняются. Старый `admin` сопоставляется с существующим логином `admin`; его текущие пароль, роль, активность и почта не изменяются. Другие исторические пользователи создаются неактивными с новым случайным паролем и служебной почтой; старые пароли не переносятся.

## Предметы, кабинеты и история

Каждый предмет получает новый внутренний ID/UUID, но сохраняет **фактически записанный старый код** `EQ-*`. Новый генератор `SKX-A-*` продолжает работать независимо. Нельзя считать числовую часть EQ старым PK: в исходном снимке у 137 предметов они различаются.

ID кабинета сохраняется точной Unicode-строкой без транслитерации, смены регистра, удаления нулей или подмены похожих букв. Название берётся из исходного title, а при его отсутствии — из ID. Импортируемые кабинеты доступны для предусмотренного гостевого просмотра.

Повторяющиеся инвентарные номера не означают автоматически повторный предмет: 10 групп содержат 45 записей. Ничего не объединяется по инвентарнику, названию или похожести. Описания целиком сохраняются во внутренних заметках. Неизвестное состояние остаётся `unknown`, обслуживание — `unspecified`; импорт не утверждает, что техника исправна или ТО проведено.

Перемещения добавляются как исторические факты, а не воспроизводятся командами перемещения: текущий кабинет остаётся указанным в equipment. Неизвестные исторические версии, статусы или авторы сохраняются пустыми. Время исходника трактуется как UTC и отображается в часовом поясе сервиса.

Аудит сохраняется полностью, включая события предметов, которых уже нет. У такого события пустая новая цель и явный старый ID; предмет не воссоздаётся по одному снимку истории. Отсутствующий в исходнике автор не заменяется администратором импорта. Общая история доступна после входа в `/history`, краткая прежняя история — в карточке предмета. Исходные строки не публикуются гостям.

В текущем снимке нет вложений и истории статусов. Непустая таблица attachments останавливает импорт: сначала требуется реализовать и проверить перенос самих байтов и их хешей. ПО, лицензии и планы ТО не выдумываются из описаний и создаются отдельно по подтверждённым данным.

## Старые QR-коды

Соответствия создаются независимо:

| Исходное значение | Алиас | Цель |
| --- | --- | --- |
| Сохранённый код предмета | `asset-code:EQ-…` | Новый UUID этого предмета |
| Фактический числовой PK | `asset-id:…` | Новый UUID предмета с этим прежним PK |
| Точный ID кабинета | `location-id:…` | Новый UUID кабинета |

Поддерживаются `/eq/<code>`, `/equipment_card.php?key=…`, `code=…`, `id=…`, `/admin/equipment.php?code=…`, `/cabinet/<id>`, `/cabinet.php?id=…` и новые UUID URL. Конфликт кода или алиаса с уже существующей другой целью отменяет весь импорт.

Сохранённый активный QR из qr_codes активируется только когда его content и target_code однозначно указывают на один существующий исходный объект. Точная историческая URL-строка может иметь отдельный `url:`-алиас, в том числе при прежней опечатке имени хоста. Resolver разбирает строку локально, никогда не посещает отсканированный адрес и не перенаправляет на его хост. Другие неизвестные хосты остаются запрещёнными. Неактивная, противоречивая или потерявшая цель QR-запись сохраняется в исходном журнале с предупреждением.

В снимке 16.10.2026 QR #1 ссылается на отсутствующий `CAB-001`: новой цели у него нет. QR #2 указывает на существующий `EQ-000001`; его историческая ссылка сопоставляется явно. Это не препятствует переносу остальных меток.

Домен `skladex.vve.local` уже указывает на новый IP `.203`; DNS изменил пользователь. Ссылки с этим доменом дойдут до нового сервиса после обновления кэшей. QR с буквальным старым IP `.200` обычная камера откроет на старом сервере. Встроенный сканер нового Skladex может распознать такую разрешённую строку локально. Аналогично опечатка `skaladex` в самом QR требует исправления DNS/маршрутизации для открытия обычной камерой; алиас встроенного сканера не меняет DNS.

## Проверка результата

Сверяются не только общие количества: для каждой строки — хеш исходного payload, новый ID/UUID, код, имя, инвентарный номер, приватное описание, категория, кабинет и состояние; для всех предметов и кабинетов — независимые QR-соответствия; для истории — исходное время, снимок и удалённые цели. Ранее внесённые новые записи и счётчики кодов сравниваются с исходными хешами.

После принятия сохраняется новая резервная копия с отдельным архивом ключей и проверяется восстановление. Старый сервер не выключается и не перенастраивается этой процедурой. Дальнейшие изменения рекомендуется вести в новом Skladex; новый снимок старого сервера с исправленными уже перенесёнными строками потребует отдельной сверки, а не автоматической перезаписи.
