# Доменный вход и настройки Active Directory

## Управление через интерфейс

Откройте «Настройки → Active Directory» (/settings/directory). Здесь доступны включение доменного входа, до трёх контроллеров, LDAPS/StartTLS и порт, Base DN, NetBIOS, служебная учётная запись, доверенные CA и до 20 сопоставлений групп с ролями viewer/operator/admin. Обычный незашифрованный LDAP не допускается; проверка сертификата обязательна.

Изменять подключение может локальный администратор, подтвердив свой текущий пароль. Доменные администраторы могут посмотреть настройки и проверить текущее сохранённое подключение. Последний активный локальный администратор защищён от блокировки и понижения; его вход не зависит от AD.

Пароль служебной учётной записи никогда не выводится. Пустое поле сохраняет прежний пароль. При изменении служебного логина нужно задать пароль заново. Проверка нового сервера/CA с сохранённым служебным паролем также требует подтверждения текущим локальным паролем; пароль, введённый явно для тестового подключения, используется только в этом запросе. Пароли не попадают в old-input, аудит, диагностику или кэш идемпотентности.

CA вводится как PEM с публичными сертификатами центра сертификации. Приватные ключи, посторонние PEM-блоки, просроченные и не-CA сертификаты отклоняются. Произвольный путь к серверному файлу вводить нельзя. При отключении интеграции прежний просроченный CA можно оставить и заменить позднее.

«Проверить соединение» проверяет TLS, служебный bind, область поиска и существование разрешённых групп. Изменения не сохраняются. После проверки нового пароля его потребуется ввести ещё раз для сохранения. Для включения интеграции проверка выполняется повторно сервером; хотя бы один контроллер и все указанные группы должны быть доступны. Результат по каждому контроллеру виден отдельно.

Группа задаётся её полным DN и ролью. SID домена и RID основной группы определяются сервером по объекту AD. Совпавший RID другого домена не даёт доступ. Поддерживаются группы самого домена, вложенное членство и основная группа; BUILTIN/чужие домены сюда не относятся. Группы могут находиться в другой OU того же домена, если Base DN ограничен пользовательской OU.

## Хранение и применение

После сохранения конфигурация находится в singleton-таблице directory_configurations: весь payload зашифрован APP_KEY, модель скрывает его при сериализации. Изменение проверяет версию формы и действующие права/пароль под AUTH-SETTINGS mutex. Перезапуск PHP-FPM или правка .env для изменений через UI не требуются.

До первого сохранения используются исходные /etc/skladex/ldap.json и флаг LDAP_ENABLED как источник начальных значений. Файл root:skladex, 0640 остаётся закрытым резервом, веб-процесс его не изменяет. После появления записи БД именно она определяет конфигурацию, включая отключение: возврата к старому включённому файлу нет. LDAP_CONFIG_FILE задаёт путь исходного файла; это резервный механизм первоначальной установки.

Публичные CA из действующей конфигурации материализуются в приватном storage/app/private/directory-ca под SHA-256 содержимого. Каталог закрыт, файлы 0600, символические ссылки/подмена содержимого отклоняются; старые файлы не удаляются посреди запросов. Контроллеры обращаются к каталогу только по защищённому соединению. Требуется PHP-расширение php8.4-ldap.

Сохранение настроек отзывает все доменные сеансы и API-токены, сбрасывает кеш проверки прав. Локальные сеансы не затрагиваются. Результат LDAP, полученный до смены конфигурации, не применяется после неё: ревизия повторно сверяется под общим mutex. Отключение учитывается до 60-секундного кеша разрешений.

Послеобновлённые архивы должны содержать БД с зашифрованной конфигурацией и приватное хранилище CA. Соответствующий APP_KEY хранится в отдельном защищённом архиве /etc/skladex. Дамп без ключа не раскрывает служебный пароль; потеря ключа делает конфигурацию нерасшифровываемой.

## Идентичность и доступ

На 19.10.2026 временно разрешены Admin-NC и «Администраторы домена» с ролью администратора по указанию владельца. Группы Nextcloud, дающие всем сотрудникам доступ к облаку, сюда не переносятся. После создания отдельных групп Skladex измените DN/роли через UI.

Идентичность привязана к двоичному objectGUID. Доменные записи создаются при успешном входе; локальные записи не присоединяются по совпавшей почте или логину. Пользовательский пароль AD не сохраняется, локального пароля у доменной записи нет. Вход: доменный логин, VVE\логин или доменная почта.

Разрешение старше 60 секунд проверяется повторно. Выход из групп, отключение либо истечение учётной записи закрывают доступ и отзывают сеансы/токены; смена роли отзывает прежние сеансы/токены. При недоступности каталога просроченное разрешение не продлевается. Ручная блокировка пользователя в Skladex не снимается доменным входом. Имя, почта и роль приходят из AD.

CLI-проверка без изменения каталога и без вывода реквизитов:

    cd /srv/skladex/app
    runuser -u skladex -- php artisan skladex:directory-check

Она проверяет служебный канал и группы, но не пароль конкретного сотрудника. Реальный пароль сотрудник вводит только в обычной форме входа.

Источники: [PHP LDAP TLS](https://www.php.net/manual/en/function.ldap-set-option.php), [Microsoft AD matching rules](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/4e638665-f466-4597-93c4-12f2ebfabab5), [Microsoft primaryGroupID](https://learn.microsoft.com/en-us/windows/win32/adschema/a-primarygroupid).

Nextcloud 192.168.110.60 использовался только для чтения настроек. Его код, конфигурационные файлы и БД не изменяются.
